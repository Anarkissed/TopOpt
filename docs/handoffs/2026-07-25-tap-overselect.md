# Tap over-selection on a clean bracket — one tap selected half the model

**Date:** 2026-07-25
**Area:** app tap → selection layer (`TopOptFlows`), NOT core segmentation
**Fixture:** `core/tests/fixtures/mesh/WallMount_ShelfBracket.stl` (2224 tris, watertight,
zero non-manifold/boundary edges — needs no repair)

## Symptom

On a clean shelf-bracket STL, a single tap on one bolt-hole / strut-junction face
selected the whole diagonal strut + top bar + load region — "half the model" — instead
of the one tapped face. The user could not assign a single face an Anchor/Load role
without dragging in the strut.

## The core segmenter is exonerated (as briefed)

The core dihedral segmenter (35° default, `face_tag.cpp`) partitions this bracket into
**31 pseudo-faces**; region-grow from any single face reaches only ~12–13% of the model.
The partition is fine. The over-selection is entirely **app-side**.

## Actual mechanism (measured, not assumed)

`WorkspacePlaceholder.handlePick` → `FaceTopology.loop(fromFace:in:)` → `WorkspaceTap.route`.
For a first tap, the selection size equals the loop size, so `loop()` is the grower.

`FaceTopology.loop` was written for a **B-rep** part: OCCT can split one physical hole into
several faces (a counterbore's cylinder + cone), so tapping a *curved* face walks the
connected run of edge-adjacent curved faces to reunite them, stopping at planar faces.
"Curved" is decided by the app's own `isCurved` at a **5° threshold**.

That walk is wrong for a **mesh's pseudo-faces**. A mesh segmenter never splits a hole
across pseudo-faces — each segmented region already *is* the intended selection unit. But
on this bracket the app's 5° `isCurved` marks **18 of the 31** pseudo-faces "curved," and
they form one connected edge-adjacent component (strut walls, fillets, hole walls, top
bar). So tapping **any** of those 18 faces ran the walk and returned the whole component:

```
loop(face 9)  = [0,1,3,4,5,6,9,10,12,16,17,18,19,20,21,25,28,29]  (18 faces)
              = 983 / 2224 triangles = 44% of the model  ← "half the model"
```

Key point: the app re-derived topology at a **different, much looser threshold (5°)** than
the segmenter (35°) and then **unioned across it** — crossing exactly the fillets/edges the
core would not cross. The pseudo-face id map itself was correct and not stale; the bug was
running a B-rep hole-reunion walk over a mesh partition that never needed it.

## Fix

`FaceTopology.loop` now short-circuits to `[face]` when the mesh carries pseudo-faces:

```swift
if mesh.pseudoFaces { return [face] }
```

To know this at the tap site, `pseudoFaces` (already on `ImportedMesh` from the bridge) is
threaded onto `ViewerMesh` and set at its only face-carrying construction site
(`ProjectModel`; every other `ViewerMesh` is an optimized result with no faces). STEP
imports keep `pseudoFaces == false`, so the B-rep loop walk is unchanged for them.

This also fixes the paint path (`PaintInteraction` calls the same `loop()`), and preserves
determinism (`loop` stays a pure function of the mesh).

## Bars — met

- **Tapping selects the one face, bounded and asserted.** New
  `FaceSelectionTests.testShelfBracketTapSelectsSinglePseudoFace` imports the committed STL
  and asserts, for **every** pseudo-face, `loop(f) == [f]` and its triangle coverage ≤ 25%
  of the model (region-grow reaches ~12–13%; the real bound is one face). This test **fails
  on the pre-fix code** (41 assertion failures, up to 983/2224 tris) and passes after.
- **Back column → column face, not the strut.** The assertion covers the right wall-mount
  leg's faces (7,8,11,13,14,15) among all others — none over-select.
- **Determinism preserved.** `loop()` is unchanged for B-rep; the l-bracket single-face-hole
  test and the synthetic multi-face octagon loop test still pass.
- **swift test:** 729 tests, 0 failures, 3 env-skipped (86 s).
- **Screenshot:** real Metal viewer, before/after, in `docs/handoffs/assets/`:
  - `tap_overselect_before.png` — one tap lights the top bar + entire diagonal strut.
  - `tap_overselect_after.png` — the same tap selects exactly one face.
  Generated by `TapOverselectCaptureTests` (GPU + STL-import gated), which renders the
  committed fixture and reproduces the pre-fix union locally from the public
  `adjacency`/`isCurved` API (so the BEFORE image is faithful without resurrecting the bug
  in product code).

## Follow-ups (not done here)

- The app's `isCurved`/`adjacency`/loop machinery is now **dead for meshes** and only used
  for STEP. If STL/3MF ever want a genuine multi-pseudo-face selection (e.g. "select the
  whole bore" when the segmenter *does* split it), do it from the segmenter's own adjacency
  at 35°, not a second 5° pass.
- The bridge still does not forward the core's exact `StepSurfaceKind`; the 5° `isCurved`
  heuristic for STEP remains (unchanged here). A real kind would remove the last threshold
  guess. See the M7.5 handoff.
