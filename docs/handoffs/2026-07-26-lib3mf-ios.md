# 3MF import on iPad — provision iOS lib3mf and make its absence LOUD

**Date:** 2026-07-26
**Area:** `app/scripts/build_occt_ios.sh`, `app/scripts/build_core.sh` (build/observability only — no runtime code changed)
**Evidence:** `docs/handoffs/evidence/2026-07-26-lib3mf-ios/`

---

## TL;DR

The maintainer's iPad refused a `.3mf` with *"3MF import requires lib3mf, which
is not available in this build"* even after a full rebuild + reinstall. That
message is **correct** — the build genuinely shipped without iOS lib3mf. The real
defect was that **the build never said so.** It reported a clean, confident,
successful run and left 3MF-on-iPad silently missing.

Two things were wrong and are now fixed:

1. **The iOS lib3mf stage failed silently.** On this machine (CMake 4.4.0) lib3mf
   v2.3.2's `cmake_minimum_required(VERSION 3.0)` is rejected outright — modern
   CMake removed pre-3.5 compatibility. The old `build_lib3mf` swallowed that
   (configure failed → build failed → no dylib → a mid-function `return 0`), and
   the driver's `build_lib3mf || echo warn` let the warning scroll past hundreds
   of lines of OCCT output. **This is the most likely cause of what the
   maintainer hit.** Fixed two ways: (a) a `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`
   compat shim so the pinned lib3mf actually configures under CMake 4.x, and
   (b) every failure path now records a reason and is re-printed at the **end of
   the run** as a loud `FAILED ❌` / `SKIPPED` / `BUILT ✅` block.

2. **`build_core.sh`'s vendored report never mentioned iOS lib3mf.** It printed a
   macOS lib3mf line and an iOS *OCCT* line but was silent on iOS *lib3mf*. It now
   prints an explicit presence/absence line in the same voice as the OCCT line,
   including the exact command to fix an absence, and shouts if the state is
   half-built (core-compiled-with-lib3mf but no embedded xcframework, or vice
   versa).

**BLOCKED-STOP did not trigger:** lib3mf **does** cross-compile for iOS (v2.3.2,
device + simulator, arm64), and the resulting iOS-arch binary reads a real `.3mf`
on an iOS runtime. Evidence below.

## Root cause (verified)

```
$ cmake --version
cmake version 4.4.0

# lib3mf v2.3.2/CMakeLists.txt line 1:
cmake_minimum_required (VERSION 3.0)

# configure, exactly as the old script ran it:
CMake Error at CMakeLists.txt:1 (cmake_minimum_required):
  Compatibility with CMake < 3.5 has been removed from CMake.
  ...
  Or, add -DCMAKE_POLICY_VERSION_MINIMUM=3.5 to try configuring anyway.
-- Configuring incomplete, errors occurred!
exit=1
```
(`evidence/00_root_cause.txt`, `evidence/01_prefix_configure_fails.txt`)

Why the old code hid it: `build_lib3mf` is called as `build_lib3mf || echo warn`,
which **disables `set -e` for the whole function body.** So a failed
`cmake --build` did not abort — execution fell through to the framework-wrapping
loop, found no dylib, and hit `[[ -n "$dylib" ]] || { echo warn; return 0; }`.
**Return 0.** The driver saw success, the manifest was written, and the summary
declared the OCCT slices ready with no hint that 3MF was gone.

This is the "instruments without alarms" failure named in handoff 169: the data
was on screen (a warn line, far up), but nothing at the end forced the operator
to see it.

## What changed (build/observability only)

`git diff --stat`:
```
 app/scripts/build_core.sh     | ~30 +++
 app/scripts/build_occt_ios.sh | ~140 ++++++++++-----
```
No runtime/C++/Swift changed. The runtime refusal in `core/src/io/part.cpp` is
**untouched** (L5): a build genuinely without lib3mf still refuses `.3mf` clearly.

### `build_occt_ios.sh`
- `build_lib3mf` is now **defensive**: every fallible step (`git clone`, each
  slice's configure / build / install, the dylib check, the `xcframework`
  packaging) is checked explicitly and, on failure, sets `LIB3MF_DETAIL` and
  returns non-zero. The silent `return 0` is gone.
- Configure now passes `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` — a compat shim for
  the **pinned** lib3mf under CMake 4.x. This is **not** a version change; it
  lets the existing v2.3.2 tag configure. No-op on CMake 3.x and if lib3mf is
  ever bumped to a tag whose minimum is ≥3.5.
- The driver tracks `LIB3MF_STATUS` (`ok|failed|skipped`) and the **end-of-run
  summary** prints a dedicated block: `BUILT ✅` (with paths), `FAILED ❌` (with
  the reason and the re-run command), or `SKIPPED`. A failure can no longer be
  lost in the scrollback.

### `build_core.sh`
- The `==> vendored:` report now prints an **iOS lib3mf line** mirroring the OCCT
  line: present ("3MF import is available on iPad/simulator"), absent ("`.3mf`
  import will be UNAVAILABLE on iPad" + the exact fix command), or a loud
  `WARNING: iOS lib3mf is INCOMPLETE` when only one of {compiled-in core,
  embedded xcframework} is present.
- The per-slice build log line now appends `+ lib3mf` when the slice compiles it
  in, so even the scrolling build output is honest.
- The simulator slice is forced arm64-only when **OCCT *or* lib3mf** iOS is
  present (both cross-built deps are arm64-only) — previously only OCCT drove
  this, so a lib3mf-only build could produce a fat sim slice that fails to link
  lib3mf on x86_64.

## Bars

### L1 — WITHOUT iOS lib3mf: build still succeeds, report says 3MF unavailable
Actual `build_core.sh` output on a checkout with no iOS lib3mf
(`evidence/04_build_core_WITHOUT_ios_lib3mf.txt`):
```
==> vendored:
    .../vendor/TopOptCore.xcframework (macos-arm64, ios-arm64-simulator, ios-arm64)
    ...
    (no vendor/occt-ios — iOS slices are OCCT-free; run build_occt_ios.sh for STEP on iOS)
    (no vendor/lib3mf-ios — iOS slices are 3MF-free; .3mf import will be UNAVAILABLE on iPad.
     run 'BUILD_LIB3MF=1 ./app/scripts/build_occt_ios.sh' then re-run this script to enable 3MF on iOS)
==> done. Test: (cd .../app/TopOptKit && xcodebuild test -scheme TopOptKit-Package -destination 'platform=macOS')
```
Build **succeeded** (`==> done`) and the absence is stated plainly with the fix.

### L2 — WITH iOS lib3mf: report says so, and the framework is real
`build_core.sh` report with iOS lib3mf present
(`evidence/05_build_core_WITH_ios_lib3mf.txt`):
```
    .../vendor/lib3mf-ios/lib3mf.xcframework  (lib3mf, iOS device+sim — linked+embedded on iOS)
    iOS slices built WITH lib3mf: 3MF import is available on iPad/simulator.
```
The packaged xcframework carries both device and simulator slices
(`evidence/02_ios_dylib_arch_platform.txt`):
```
== iphonesimulator ==  archs: arm64   platform IOSSIMULATOR  minos 16.0
== iphoneos ==         archs: arm64   platform IOS           minos 16.0
lib3mf.xcframework/{ios-arm64, ios-arm64-simulator}/lib3mf.framework
```
**Not produced:** a fully-linked `.app` bundle Frameworks listing from
`xcodebuild` on the app target. See "What I could not produce" below.

### L3 — the payload: a real `.3mf` imported on an iOS destination, succeeding
An iOS-simulator-arch binary loaded the cross-built lib3mf and read the real
`core/tests/fixtures/mesh/plate_bore.3mf` **on the iOS simulator runtime**, using
the same dynamic-load + mesh API as `core/src/io/threemf.cpp`
(`evidence/03_ios_sim_reads_real_3mf.txt`):
```
$ xcrun simctl spawn <iPhone 17 / iOS 26.5> ios_3mf_probe <sim lib3mf.dylib> plate_bore.3mf
lib3mf runtime version: 2.3.2
READ OK: .../plate_bore.3mf
vertices=208 triangles=416
PROBE_EXIT=0
```
This proves the **payload** — the iOS-arch lib3mf parses a real `.3mf` on an iOS
runtime. It is **not** a full app-UI import through the document picker on a
physical iPad (see below).

### L4 — macOS/worker 3MF unaffected
The diff touches only iOS scripting; the macOS slice logic in `build_core.sh` and
every macOS-path file (`build_lib3mf_macos.sh`, `Package.swift` macOS gate,
`core/src/io/threemf.cpp`, `core/CMakeLists.txt`) are unchanged. Re-proven
functionally: macOS lib3mf **2.5.0#1** (CI pin) reads the same fixture identically
(`evidence/11_macos_2.5.0_reads_same_3mf.txt`), and `topopt-cli` (DEPS=ON, the
worker's exact binary) still imports `.3mf` — see `evidence/12_macos_build_cli.txt`
and `evidence/13_cli_3mf_worker_real.txt`.

### L5 — runtime refusal not weakened
`core/src/io/part.cpp`'s `#else` branch is untouched; a lib3mf-free build still
throws *"3MF import requires lib3mf, which is not available in this build; export
the part as STL and import that instead."* The fix removes the **silent** path to
that message, not the message.

## Version split (investigation — no version silently changed)

- **iOS** builds lib3mf **v2.3.2** from source (`build_occt_ios.sh` `LIB3MF_TAG`).
- **macOS/worker** pins vcpkg **2.5.0#1** (CI's exact version;
  `build_lib3mf_macos.sh`).

This divergence is **known and one-sided**: the 2026-07-25 macOS handoff
explicitly called the old hand-built 2.3.2 "a mismatch" and moved macOS **to**
2.5.0 to match CI — iOS was simply never brought along. It is now the lone
straggler.

**Is it safe for round-tripping the same `.3mf`?** For the app's actual import
path — **yes, and it's measured.** `read_3mf_file` reads only `<mesh>` vertices +
triangle indices through the oldest, most stable 3MF-Core API
(`QueryReader("3mf")` → `GetMeshObjects` → `GetVertices` / `GetTriangleIndices`),
unchanged across all lib3mf 2.x. The same `plate_bore.3mf` yields **identical
geometry on both versions**:

| version | slice | vertices | triangles | v0 |
|---|---|---|---|---|
| 2.3.2 | iOS sim | 208 | 416 | (3.000, 0.000, 0.000) |
| 2.5.0 | macOS | 208 | 416 | (3.000, 0.000, 0.000) |

(`evidence/03_...` vs `evidence/11_...`)

**Recommendation (for the maintainer, not applied):** align iOS to the CI pin
(bump `build_occt_ios.sh` `LIB3MF_TAG` from `v2.3.2` to `v2.5.0`) so the "same
file → same result on every slice" guarantee the macOS pin established holds
everywhere. 2.5.0 has ~2 years of parser hardening / stricter validation over
2.3.2, so while well-formed mesh files agree, malformed or exotic-extension files
could be accepted on one slice and rejected on the other. The interim risk is low
(mesh-only import, measured parity), so this is a **should**, not a **must**.

The precondition is met: **2.5.0 cross-configures for iOS** (simulator, exit 0,
`evidence/14_lib3mf_2.5.0_ios_configure.txt`) — and it declares
`cmake_minimum_required(VERSION 3.10)`, i.e. ≥3.5, so it needs **no**
`CMAKE_POLICY_VERSION_MINIMUM` shim under CMake 4.x. Aligning would therefore both
close the version split **and** let the shim added here be dropped. Caveat: I ran
a configure-only smoke test, not a full 2.5.0 iOS build; a bump should be
validated with `BUILD_LIB3MF=1 ./app/scripts/build_occt_ios.sh` end-to-end.

Per the task, `LIB3MF_TAG` was **not** changed here.

## What I could not produce (stated, not implied)

- **A physical-iPad app-UI import.** No iOS device was available. L3 is proven at
  the payload level (iOS-arch lib3mf reads a real `.3mf` on the simulator
  runtime), not as a tap-through-the-document-picker on hardware.
- **A full `xcodebuild` app-bundle Frameworks listing.** L2 is proven at the
  xcframework level (device + simulator `lib3mf.framework`, correct arch /
  platform / install-name) and at the `build_core.sh` report level. I did not
  drive a full app-target archive to enumerate `MyApp.app/Frameworks/`.

Both gaps are about the *end-to-end app packaging/UI*, not about whether lib3mf
works on iOS — that is demonstrated.

## How to reproduce

```bash
BUILD_LIB3MF=1 ./app/scripts/build_occt_ios.sh   # cross-builds OCCT + lib3mf for iOS
./app/scripts/build_core.sh                       # detects them; report states 3MF on iPad
# then build/run the app on an iPad sim/device and import a .3mf
```
On a checkout without the iOS lib3mf trees, both scripts still succeed and both
now say — loudly, at the end — that 3MF will be unavailable on iPad, with the one
command that fixes it.
