## 0. What was actually wrong

The 3MF *code* was complete and the build/CI *config* already named lib3mf — but
the **import path had never once executed**, and nothing committed proved it. The
mesh-optimize handoff (2026-07-24-mesh-optimize-path §7) said so in as many words:

> **3MF is code-complete but unexercised here** — lib3mf is not installed in this
> environment … `import_part_file` on a `.3mf` compiles and dispatches … but was
> never run … treat as untested until then.

So the standing state was: `read_3mf_file` (the writer/reader round-trip in
`test_3mf`) and 3MF *output* from a STEP part (`cli_demo`) were exercised in CI,
but **no test ever imported a real `.3mf` part, segmented it, and optimized it**,
and nothing proved an STL and a 3MF of the same part agree. The app's "3MF import
requires lib3mf, which is not available in this build" sheet
(`part.cpp:44`) is correctly gated on `TOPOPT_HAVE_3MF` — it can only appear when
lib3mf genuinely isn't in the build — but that gate had never been walked from
the *present* side end to end.

This task walks it: install the dependency for real, **execute the code that was
never run**, fix what surfaced, and commit the proof.

## 1. The dependency was already locked — I made it real and ran it

`core/vcpkg.json` already lists `lib3mf`; `.github/workflows/ci.yml` already
configures with `-DTOPOPT_REQUIRE_DEPS=ON`, which turns
`find_package(lib3mf CONFIG REQUIRED)` on and fails the build if it is missing;
`core/CMakeLists.txt` already compiles `src/io/threemf.cpp` and defines
`TOPOPT_HAVE_3MF` under `if(lib3mf_FOUND)`. **The Configure step names lib3mf and
CI has been building it all along** (`evidence/.../ci_and_build_config.txt`). No
manifest/CI change was needed to *enable* the dependency — it was enabled; it was
just unproven from the import side.

To actually run it (this env, like every prior one, had no lib3mf), I built
lib3mf **2.3.2** from the upstream Darwin release package and pointed the core
build at it (`-Dlib3mf_DIR=…/lib/cmake/lib3mf`, brew OCCT + Eigen). This is the
**first execution of the 3MF path outside CI's build-only reach**, and the first
time the import→segment→optimize chain has run anywhere.

## 2. What executing the code surfaced

**`export_3mf` passes for real** — 21 checks, the write/read round-trip on a solid
block and a genus-1 body. Previously compiled-in but never locally run.

**One honest correction to the writer's contract.** `threemf.hpp` claimed a
re-import "reproduces the geometry to float precision." Executing it and reading
the package back shows lib3mf serializes vertices as **~6-significant-digit
decimal text** in the XML (`<vertex x="2.974334" …/>`), a hair coarser than the
float32 3MF nominally stores. For a part sized in mm the round-trip delta is
**≤ 9.5e-7 mm** (measured on `plate_bore`), and the enclosed-volume delta
**1.96e-8** relative — both far below one voxel, but not "float precision." The
header comment now states the measured behaviour. (No code change — the writer is
correct; only the promise was overstated.)

## 3. A real 3MF fixture, and STL-vs-3MF equivalence

`core/tests/fixtures/mesh/plate_bore.3mf` is a **real OPC/3MF zip package**
(`3D/3dmodel.model` + `[Content_Types].xml` + `_rels/.rels`,
`evidence/.../fixture_is_real_3mf.txt`). It is the 3MF encoding of the *same*
part as the committed `plate_bore.stl`: produced by reading that STL and writing
it back with `write_3mf_file`, i.e. the two files are one geometry in the two
formats a user exports from CAD. (Regenerate: read the STL → `write_3mf_file`.)

`threemf_import` section A imports both via `import_part` and proves they agree
where it counts (`stl_vs_3mf_equivalence.txt`):

```
STL-vs-3MF plate_bore equivalence (max vertex diff 9.537e-07 mm, vol rel diff 1.955e-08):
   res | grid       |  solid | solid-diff | per-face tags identical
    16 | 16x11x 3   |    486 |     0      | yes
    24 | 24x16x 4   |   1408 |     0      | yes
    32 | 32x22x 6   |   3110 |     0      | yes
    48 | 48x32x 8   |  11392 |     0      | yes
    64 | 64x43x11   |  28072 |     0      | yes
```

* **Topology + segmentation are bit-identical**: same triangle indices, same
  `face_count`, same per-triangle pseudo-face id — the two files carry the same
  mesh connectivity, so the dihedral segmenter manufactures the identical faces.
* **The grid the optimizer solves on is identical**: `solid-diff = 0` (the exact
  set of occupied voxels matches) at every resolution, and every one of the 7
  pseudo-faces tags the identical voxel set from either file. The ≤1e-6 mm vertex
  rounding never moves a voxel.

## 4. A 3MF part, optimized end to end — byte-identical to the STL run

`threemf_import` section B runs `run_job` on `plate_bore.3mf`: import → segment
(7 pseudo-faces) → voxelize @32 → tag the r=3 bore FIXTURE → self-weight ladder →
gate → **report + variants + fields**, the same shape a STEP job produces. Two
variants accepted, each with a finite positive margin; deterministic twice-run
(byte-identical report + meshes + pseudo-face ids).

Because the voxel grid + tags are identical to the STL's (§3), **the entire run
is byte-identical between the STL and the 3MF of the same part**
(`stl_vs_3mf_byte_identity.txt`): same 2197-byte report, same exported
marching-cubes meshes, same margins to full double precision
(28720.459447 / 21305.637827). The optimizer never sees the raw coordinates —
only the grid — so the format the part arrived in cannot change the result. This
is the strongest form of the "STL and 3MF agree" bar.

```
stl: faces=7 fixmatch=1 evaluated=2 accepted=2
3mf: faces=7 fixmatch=1 evaluated=2 accepted=2
report byte-identical: 1
```

The test additionally asserts the exported variant meshes are byte-identical
(`read_file(rstl.mesh_paths[i]) == read_file(r3mf.mesh_paths[i])`), which follows
from the identical density grid feeding marching cubes.

## 6. Scope honesty

* **Build/CI config was already correct** — lib3mf is in the manifest and the
  Configure step requires it. This change did not need to *add* the dependency;
  it added the missing *proof* (a committed import fixture + the import/optimize
  test) and ran the path for the first time. The "CI config" evidence records the
  existing wiring plus the CMakeLists diff that registers the new gate.
* **lib3mf 2.3.2 locally vs the vcpkg-pinned build in CI.** I built 2.3.2 to run
  the code here; CI installs lib3mf from the pinned vcpkg baseline. The public API
  used (`CWrapper::loadLibrary`, `SetGeometry`, `GetVertices`/`GetTriangleIndices`,
  the `sPosition`/`sTriangle` structs) is stable across lib3mf 2.x, and the
  writer/reader are unchanged, so CI exercises the identical source. The 6-decimal
  serialization is a property of the 3MF text format, not of 2.3.2 specifically.
* **iOS slice still has no lib3mf.** The OCCT-free iOS build does not link lib3mf,
  so on-device 3MF import still shows the (correctly gated) "not available in this
  build" sheet. Bringing lib3mf to the app slice is an app-build task, out of this
  core/build/CI scope; core, the CLI, and the LAN worker — every build that runs
  `run_job` — now import 3MF for real.
