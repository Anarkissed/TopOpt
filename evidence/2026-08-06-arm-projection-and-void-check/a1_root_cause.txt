WHICH OF MY CHANGES? ISOLATED WITH THE CLI, NOT ARGUED
-------------------------------------------------------
Same two job documents the test builds, run through the branch's own
`topopt-cli`, with `output.project_cad_faces` explicitly set:

    project_cad_faces=on  : STL-input vs 3MF-input exported meshes identical?  no
    project_cad_faces=off : STL-input vs 3MF-input exported meshes identical?  YES

Arming projection is the cause. The weld guard only runs INSIDE projection, so
this alone does not separate "projection ran" from "the weld key inside it" —
the magnitudes do:

    variant_040.stl: 1079 of 6972 corners differ; max 4.7684e-07 mm; median 2.3842e-07 mm
    variant_060.stl: 1007 of 8928 corners differ; max 4.7684e-07 mm; median 2.3842e-07 mm

A different weld-guard DECISION reverts a vertex, moving it by up to one voxel —
about 1.5 mm on this part at resolution 32. What is observed is ~1000 corners
differing by ~2.4e-07 mm: SIX ORDERS OF MAGNITUDE too small to be a reverted
vertex, and three orders too many vertices. That is a pervasive last-bit
difference, which is the signature of the projection TARGETS differing, not of
the guard choosing differently.


★ ROOT CAUSE, WITH FILE AND LINE
---------------------------------
`core/src/io/segment.cpp:185` fits a plane from a patch's MEAN NORMAL, and
`:280` fits a cylinder by LEAST SQUARES within `cylinder_radius_tolerance`. So an
STL/3MF import's `StepModel::faces` carry `StepSurfaceKind::Plane` and
`::Cylinder` that were ESTIMATED FROM THE IMPORTED MESH — they are not
statements, they are fits.

`core/src/cli/run_job.cpp` gated projection only on `!cad->faces.empty()`, which
is true for those manufactured faces. So arming `project_cad_faces` by default
turned projection on for mesh parts, projecting exported vertices onto surfaces
fitted from the very mesh being exported.

Because the fit is computed FROM the imported vertices, and STL stores float32
while 3MF stores full-precision decimal text, the two imports fit slightly
different surfaces — and the exports diverge by exactly one float32 quantum.

★ AND IT IS A CORRECTNESS BUG, NOT ONLY A TEST FAILURE. PR 307's justification
for projection is that moving a vertex onto its own analytic surface is
dimensionally exact BECAUSE the B-rep states that surface; `job.hpp` says in
as many words "nothing is averaged, no surface is estimated". On a mesh part
both of those are false. The test caught it because a fitted surface is
input-format-dependent, but the problem would be there on a single format too:
the geometry is being snapped onto a guess about itself.


THE FIX
--------
`StepModel::faces_are_fitted` (core/include/topopt/step.hpp), set false by the
STEP path (core/src/io/part.cpp:507) and true by the mesh path (:551), and
`export_variant_mesh` now requires `!cad->faces_are_fitted`. Projection runs
where the surfaces were READ and not where they were FITTED.
